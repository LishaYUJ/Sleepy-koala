# 注册可靠性、CORS、健康检查与幂等性笔记

## 1. `Failed to fetch` 到底代表什么

`Failed to fetch` 是浏览器 `fetch()` 的通用网络错误。它只能说明前端没有拿到一个可以交给 JavaScript 使用的正常响应，不能单独证明后台没有执行请求。

常见原因包括：

- 后端没有启动或正在冷启动；
- DNS、网络或 TLS 连接失败；
- CORS 响应头缺失，浏览器主动拦截响应；
- 请求超时或连接中途断开；
- Azure、反向代理或网关返回临时错误；
- 请求已经在后台完成，但返回前端时连接断开。

因此：

```text
前端看到 Failed to fetch
不等于
后台一定没有处理请求
```

## 2. CORS 是什么

CORS（Cross-Origin Resource Sharing）是浏览器执行的跨域访问规则。

Sleepy Koala 的两个 origin 不同：

```text
前端：https://msa-sleepy-koala.vercel.app
后端：https://sleepy-koala-lisa.azurewebsites.net
```

浏览器要求后端响应包含类似下面的头：

```http
Access-Control-Allow-Origin: https://msa-sleepy-koala.vercel.app
```

如果缺少这个头，即使服务器真的返回了内容，浏览器也可能不允许前端 JavaScript 读取。

### 预检请求

发送 JSON 的跨域 `POST` 之前，浏览器通常先发送：

```http
OPTIONS /api/auth/register
```

这叫 preflight（预检）。浏览器用它确认目标服务器是否允许这个 origin、请求方法和请求头。

如果预检失败，真正的 `POST` 通常不会发送。如果 `POST` 已经发送但响应缺少 CORS 头，后台可能已经处理了请求，而前端仍然只能看到 CORS 或 fetch 错误。

## 3. 冷启动与真正的 CORS 配置错误

看到 CORS 错误，不一定代表应用中的 CORS 配置写错了。

如果 Azure App Service 正在休眠、冷启动、重启或暂时不可用，响应可能来自 Azure 平台，而不是 ASP.NET 应用。平台响应不会经过应用中的 CORS 中间件，所以也可能缺少 CORS 头。

判断方式：

- 检查 `/health` 是否正常；
- 在 Network 面板检查 `OPTIONS` 和 `POST` 是否都出现；
- 查看响应状态码和响应头；
- 重复检查恢复后的响应；
- 对照 Azure App Service 日志。

如果服务恢复后持续返回正确的 CORS 头，问题更可能是临时启动或平台状态，而不是永久配置错误。

## 4. 健康检查的作用

健康检查的目标是先确认服务器可以响应，再发送敏感或会修改数据的请求。

```text
点击注册
  -> GET /health
  -> 后端健康
  -> POST /api/auth/register
```

健康检查只发送一个无敏感信息的 `GET`，不包含邮箱或密码。

### 三种不同的时间概念

```text
单次健康请求最多等待 5 秒
失败后等待 2 秒再检查
整个自动注册流程最多持续 3 分钟
```

- 5 秒：一条健康请求最多等待多久回复。
- 2 秒：一次失败后，下一次检查前的间隔。
- 3 分钟：健康检查、注册提交和自动恢复加起来的总上限。

它们不是“平时每 5 秒检查一次”。只有用户执行登录或注册时，前端才启动这个流程。

## 5. 健康和就绪并不完全相同

当前 `/health` 主要说明 ASP.NET 应用可以响应。

它不一定证明：

- SQL 数据库一定可以连接；
- 数据库迁移已经完成；
- 所有依赖服务都正常；
- 下一毫秒服务器不会重启。

更严格的系统通常区分：

- liveness：进程是否活着；
- readiness：应用是否已经准备好处理真实业务，包括数据库等依赖。

## 6. 为什么注册请求不能像健康检查一样随便重试

健康检查是只读操作，重复执行不会修改数据。

注册是状态修改操作：它会创建用户。如果响应中途断线，可能出现：

```text
情况 A：请求没有到达后台，账号没有创建
情况 B：后台已经创建账号，但响应没有回到前端
```

前端看到的都可能只是 `Failed to fetch`。

如果没有额外保护就自动重新注册，可能重复执行同一个业务操作。

## 7. 幂等性是什么

幂等性表示：同一个业务操作重复执行多次，最终效果与执行一次相同。

Sleepy Koala 为每次注册生成：

```text
registrationAttemptId = 一个随机 UUID
```

注册和所有自动重试都使用同一个 ID。

后台规则：

```text
没见过这个 ID
→ 创建账号

见过这个 ID，而且资料相同
→ 返回原账号，不再创建

见过这个 ID，但资料不同
→ 拒绝请求
```

## 8. 什么算“同一次注册”

以下过程属于同一次注册：

```text
点击 Create Account
→ 第一次发送
→ 响应断线
→ 自动恢复
→ 自动重发
→ 最终超时后，在未修改资料的情况下点击 Try Again
```

这些步骤使用相同的 `registrationAttemptId`。

以下情况会开始新的注册操作并生成新 ID：

- 修改邮箱；
- 修改昵称；
- 修改密码或确认密码；
- 切换登录/注册模式；
- 刷新或重新打开页面；
- 后台发现旧 ID 与资料冲突。

## 9. “相同 ID + 不同资料”是什么意思

假设第一次请求是：

```text
ID：abc-123
邮箱：a@example.com
昵称：Koala
密码：Password123
```

以下任意变化都属于相同 ID 携带不同资料：

- 邮箱不同；
- 昵称不同；
- 密码不同；
- 三项都不同。

正常网页会在用户修改资料时生成新 ID，所以这种情况主要用于防御前端 bug、手工 API 请求、并发旧请求或恶意调用。

确认密码不会发送到后台，因此不参与后台比较，但修改确认密码仍会让前端开始新的注册尝试。

## 10. 操作 ID和邮箱唯一索引的区别

两者提供不同层次的保护：

```text
registrationAttemptId 唯一
→ 保护同一次操作的自动重试

Email 唯一
→ 防止不同操作创建重复邮箱账号
```

刷新页面后，内存中的操作 ID会丢失。如果第一次注册已经成功，用户重新注册时会生成新 ID，但邮箱唯一索引会阻止第二个账号，并提示用户登录。

## 11. 最终统一自动循环

```text
验证表单
  -> 创建或复用操作 ID
  -> 检查 /health
  -> 发送注册
  -> 网络/CORS/502/503/504 异常
  -> 等待 2 秒
  -> 返回健康检查
  -> 用相同 ID重发
  -> 收到明确响应，或达到 3 分钟总上限
```

自动重试的情况：

- 网络断开；
- CORS 被浏览器表现为 fetch 失败；
- 响应途中断线；
- HTTP `502`、`503`、`504`。

不自动重试的情况：

- 邮箱已存在；
- 数据验证失败；
- 相同操作 ID与资料冲突；
- 其他明确的业务错误。

原因是明确的业务错误不会因为等待两秒而自动消失。

## 12. 用户界面与真实业务逻辑应该分离

普通用户不需要看到 CORS、操作 ID、幂等重放或请求阶段。

当前简化界面：

```text
等待或恢复服务器：Starting the server…
提交注册：Creating your account…
处理中按钮：Please wait…
最终失败：We couldn’t connect to the server. Please try again.
重试按钮：Try Again
```

复杂的内部状态仍然存在，只是不展示给用户。

## 13. React 状态与 JSX 显示逻辑

业务函数负责改变状态：

```text
register() 设置 authPhase / isLoading
```

JSX 负责把状态翻译为界面：

```tsx
{isLoading
  ? 'Please wait…'
  : isLogin
    ? 'Sign In'
    : 'Create Account'}
```

三元表达式：

```text
条件 ? 条件为真时的结果 : 条件为假时的结果
```

嵌套三元表达式表达的是判断优先级，不是从上到下依次显示多个文本。

## 14. 为什么旧代码先判断 `isWakingServer`

旧状态中，服务器启动时通常同时满足：

```text
isWakingServer = true
isLoading = true
```

所以必须先判断更具体的 `isWakingServer`。如果先判断 `isLoading`，程序会立即选择 `Processing...`，永远不会到达 `Waking up server...` 分支。

## 15. 用户提示与开发日志应该分开

用户只需要知道当前是否需要等待或采取操作。

开发者需要知道：

- 健康检查失败次数；
- 已经等待多久；
- 注册发送次数；
- 是否发生网络恢复；
- 后台是创建还是幂等重放。

浏览器 DevTools：

- Console 显示 CORS、网络错误和应用诊断事件；
- Network 显示 `OPTIONS`、`GET /health`、`POST`、状态码、耗时和响应头。

后台日志记录：

- `RegistrationCreated`
- `RegistrationReplayed`
- `RegistrationUserAlreadyExists`
- `RegistrationIdempotencyConflict`

日志不应记录密码、邮箱、昵称或完整操作 ID。

## 16. 浏览器日志和后台日志看到的范围不同

```text
请求没有到达后台
→ 浏览器能看到失败
→ 后台没有记录

请求到达并完成，但响应断线
→ 后台能看到成功
→ 浏览器只看到网络失败
```

排查分布式问题时需要同时看前端 Network/Console 和后台日志。

## 17. 数据库唯一索引为什么重要

应用代码先查询再创建仍然可能出现并发竞态：

```text
请求 A 查询：不存在
请求 B 查询：不存在
请求 A 创建
请求 B 也尝试创建
```

数据库唯一索引是最终保护层。即使两个请求同时到达，数据库也只允许一个相同操作 ID或邮箱成功写入。

应用捕获唯一约束导致的 `DbUpdateException` 后，会重新查询：

- 如果相同操作已经完成，返回幂等重放结果；
- 如果邮箱被占用，返回 `UserExists`；
- 如果都不是，则重新抛出异常。

## 18. HTTP 错误分类

大致可以分为：

```text
400/409
→ 请求或业务状态有明确问题
→ 不自动重试

502/503/504
→ 网关或服务临时不可用
→ 可以自动重试

网络异常 / Failed to fetch
→ 结果可能未知
→ 幂等操作可以自动重试

500
→ 应用内部错误
→ 当前方案不自动重试，避免掩盖程序缺陷
```

## 19. Azure 可用性措施的区别

### 前端健康检查

用户开始操作时等待服务器就绪，保护当前这次操作。

### 外部定时健康检查

监控服务周期访问 `/health`，减少长时间无人访问导致的休眠，但不能保证服务器永远可用。

### Always On

由 Azure 持续保持应用进程运行。如果 App Service 套餐支持，它通常比外部定时访问更可靠。

### Azure Health Check

用于判断实例健康和处理异常实例，不等同于持久化用户请求，也不完全等同于 Always On。

## 20. 数据库迁移与部署顺序

幂等注册增加了 `RegistrationAttemptId` 数据库字段和唯一索引，所以部署前必须执行迁移。

推荐顺序：

```text
1. 应用数据库迁移
2. 部署新前端
3. 部署新后端
4. 验证健康检查、CORS、注册、重放和登录
```

旧后端会忽略新前端多发送的 JSON 字段，因此先部署前端可以减少不兼容窗口。

## 21. 测试应该覆盖什么

后端：

- 相同 ID和相同资料返回同一个用户；
- 相同 ID和不同资料被拒绝；
- 数据库只存在一个用户；
- CORS 预检正确；
- JWT 和现有业务接口不受影响。

前端：

- 网络断开后使用完全相同的注册 payload 重发；
- `502/503/504` 自动重试；
- 最终超时显示简单错误；
- 明确业务错误不自动重试；
- 用户状态文案和按钮正确；
- ASP.NET 验证错误被转换为可读信息。

## 22. 当前方案的边界

- 总自动恢复时间是 3 分钟，不会永久请求。
- `/health` 还不是数据库 readiness 检查。
- 页面刷新会丢失内存中的操作 ID。
- 浏览器 Console 日志不是集中式监控。
- HTTP `500` 当前不会自动重试。
- 外部 uptime 检查不能替代 Always On。

这些不是当前功能失效，而是系统可靠性的下一层改进方向。
